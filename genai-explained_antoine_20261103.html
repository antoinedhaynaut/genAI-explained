Part 0 / The map

ML vs GenAI: where does this all fit?

Key ideaClassic machine learning recognizes, classifies and predicts. GenAI creates new content. Both learn from examples. When the simpler, cheaper one does the job, use it.

"AI" gets used for everything, so let's place the terms first. Machine Learning (ML) is the broad discipline: instead of programming explicit rules, you show a program lots of examples and let it learn the pattern itself. ML has been in production in IT for 15+ years: spam filters, anomaly detection on your network, capacity forecasting, "users like you also opened this ticket." Classic ML recognizes, classifies, and predicts: it takes data in and outputs a label, a score, or a number.

GenAI (Generative AI) is a recent branch of ML where the model's output is not a label but new content: text, code, images, audio. LLMs are the text-generating flavor of GenAI, and they're what this guide focuses on. Same family, different job: classic ML tells you "this transaction looks fraudulent (94%)"; GenAI writes the fraud-investigation summary.

AnalogyClassic ML is a seasoned inspector: show it a thousand photos of defective parts and it will spot the next defect instantly, but it can only ever say "defect / no defect." GenAI is a craftsman: it studied the same photos and can now produce a report, a repair procedure, or a picture of what the fixed part should look like.
Why it matters in practiceDifferent problems, different tools. Forecasting disk usage or scoring alert severity? That's classic ML: cheaper, faster, deterministic, and often the better choice. Summarizing incidents, drafting responses, answering questions over documentation? That's GenAI. A common architecture mistake is using an expensive LLM for a job a small ML model solves better.
Part 1 / The engine

What a Large Language Model actually is

Key ideaAn LLM does one thing: predict the next token, again and again. That skill is learned once, during training, and then frozen. Everything else (answers, code, reasoning) comes from doing that one prediction very well, with the right text in front of the model.

A LLM (Large Language Model) is a program that has read a colossal amount of text (a large share of the public internet, books, code, documentation) and from all of it learned one skill extremely well: given a sequence of words, predict what comes next. That's it. There is no database of facts inside, no reasoning engine bolted on. Everything else, from answering questions to writing code and summarizing reports, emerges from doing that one prediction, billions of times, very well.

AnalogyIt's a much more powerful autocomplete. Your phone predicts the next word from your last texts; an LLM predicts it from having read more text than a human could in ten thousand lifetimes. At that scale, "predicting the next word" starts to look a lot like understanding.

Tokens: the LEGO bricks of language

Models don't work with words: they work with tokens, chunks of text of roughly 3–4 characters. "Server" is one token; "virtualization" might be three ("virtual", "iz", "ation"). Everything you send and receive is converted to tokens, and pricing, speed and limits are all measured in them. A simple rule: 1,000 tokens ≈ 750 English words.

Inside the model: the neural network

So what actually does the predicting? A neural network: a very large web of simple mathematical units, loosely inspired by how neurons connect in a brain. Each unit takes numbers in, multiplies them by its own weights, and passes a number on to the next layer. Stack dozens to more than a hundred of these layers (GPT-3 has 96), connect billions of units, and the whole network becomes a giant function: tokens go in one end, and a score for every possible next token comes out the other.

Those billions of weights are the model. They are the only thing that changes while the model learns. At the start they are random and the network outputs nonsense. It is then shown text with the next word hidden, asked to guess it, and after each guess the weights are nudged slightly so that the network would be a little less wrong next time. Repeat across trillions of examples and the weights slowly settle into values that encode grammar, facts, and patterns of reasoning. These are not stored as a lookup table anywhere, but spread across the whole network. This is why an LLM is often called a "black box": we know the weights, but no one can point to where a specific fact "lives."

AnalogyPicture the mixing desk in a recording studio, but with billions of sliders instead of a hundred. Learning is the long process of adjusting every slider until the sound coming out is right. Once set, the sliders are frozen: using the model just runs signal through that fixed configuration. Nobody can say "this one slider is the guitar"; the sound comes from all of them together.

Putting it together: predicting one token at a time

Now the full picture. Your text becomes tokens, the tokens run through the neural network, and out comes a probability score for every token that could come next. The model picks one, adds it to the text, and runs the entire thing again to get the following token. It repeats this loop (predict, append, repeat) until the answer is complete. Why it matters in practiceTwo consequences worth carrying into a customer conversation. First, an answer is built one token at a time, which is why models can start confidently and then drift. Second, because each token is chosen from a probability, the same prompt can give different answers (explained below). The fluency is real; the certainty is not guaranteed.

The context window: the model's whiteboard

The context window is how many tokens the model can "see" at once: your prompt, the conversation so far, any documents you pasted, plus its own answer in progress. Current models handle from 200,000 to about 1 million tokens, which is from a few hundred to a few thousand pages.

AnalogyThink of a whiteboard in a meeting room. Everything on the board is available to everyone; anything that gets wiped off is simply gone. The model has no memory outside the whiteboard: when a conversation "forgets" something from an hour ago, it scrolled off the board.
Nexthink exampleWorkspace (powered by Nexthink Assist) is a context window in action: it keeps track of the ongoing conversation so you can refine an investigation with follow-up questions ("now only Windows 11 devices", "break it down by location") without restarting. The conversation thread is the whiteboard.

Training vs inference: the model doesn't learn from you

A model's life has two phases. Training is when it learns, as described above: months of processing massive datasets on thousands of GPUs, costing tens to hundreds of millions of dollars. It happens once (per version), in the lab. Inference is when it's used: every prompt you send runs the frozen, finished model. Nothing you type changes the model. Your chats feel like the AI "remembers" only because the conversation stays on the whiteboard. Some products add a memory feature: they save short notes about you and put them back on the whiteboard in later sessions. The model itself still learns nothing; the product simply re-reads its notes.

AnalogyTraining is medical school; inference is seeing patients. The doctor doesn't rewire their brain after each consultation: they apply what they already learned. Notes about you live in your patient file (the context), not in the doctor's neurons.
Why it matters in practiceThis answers the #1 question colleagues will ask: "Does it learn from our data?" By default, no: inference doesn't train the model. The real questions are contractual: does the vendor log your prompts, and do they reuse them to train future versions? Enterprise plans typically guarantee they don't; consumer free tiers may not. Check the data-usage terms, not the technology.
Nexthink exampleThis is exactly what the Nexthink Global AI Hub documents. The platform's GenAI features use off-the-shelf LLMs provided by Amazon Bedrock, within Nexthink's AWS account and in the same geographical area (continent) where customer data is stored and processed. Customer data is not used to train the models. The features run inference on your telemetry; the models themselves stay frozen. When a customer asks "will our data end up in the model?", the AI Hub is the public, verifiable answer.

Cost basics: what you pay for

When a product uses a model through an API, it pays per token, at two prices. Input tokens are everything the model reads: the system prompt, the conversation so far, pasted documents, retrieved passages. Output tokens are everything it writes. Prices are quoted in dollars per million tokens, and output tokens cost more: on current flagship models, about five times more than input tokens. The reason is the loop you saw above. The whole input is read in one pass, but every output token needs its own pass through the network.

AnalogyInput tokens are the pages a consultant reads before the meeting; output tokens are the report they write afterwards. Writing takes longer than reading, so it is billed at a higher rate.
Why it matters in practiceThree things drive the bill: the size of the model, how much text is sent with each request, and how much the model writes or thinks. Long conversations cost more per message than short ones, because the whole history is sent again as input every time. Vendors give discounts for repeated input (caching) and for work that can wait (batch processing). Chat subscriptions for people usually charge a flat fee per user with usage limits; per-token pricing applies to the API that products are built on.

Hallucinations: confident nonsense

Because the model generates statistically plausible text rather than looking facts up, it will sometimes produce answers that are fluent, confident, and wrong. That's a hallucination. It's not a bug being fixed next release: it's a direct consequence of how prediction works. It cannot be removed completely, but it can be reduced a lot. Four measures work together, and most of them are covered in the rest of this guide:

  • Grounding. Give the model real data (RAG, Part 2), so it answers from your documents instead of from memory. "Grounded" means every claim can be traced back to a source, and the answer can quote it.
  • Real tools. Let an agent (Part 3) fetch live facts, such as numbers from a system, so the model does not have to guess them.
  • A second "judge" agent. A second model reviews the first answer before anyone sees it. It checks each claim against the sources and blocks or flags what is not supported. A reviewer catches errors that the author does not see.
  • Governance. Clear company rules around the model: which data it may use, which actions need a human approval, mandatory source citations, a log of every answer, and regular tests on sample questions.
Watch outAn LLM does not reliably tell you how sure it is. Newer models say "I don't know" more often, but a hallucinated ITIL process reference still reads exactly as confidently as a real one. Trust, but verify, especially for numbers, names, and citations.
Nexthink exampleThis is why Nexthink marks every AI-generated insight with the ✦ sparkles icon and explicitly recommends validating results before acting on them. Labeling AI output and keeping a human check in the loop isn't a disclaimer: it's the standard, responsible way to ship GenAI in an enterprise product.

Deterministic vs probabilistic: same prompt, different answer

Everything you've administered until now is deterministic: same input, same output, every time. Run the script twice, get the same result twice, and if you don't, it's a bug. An LLM is probabilistic: at every step it holds a distribution of candidate next tokens (as in the demo at the top) and picks among the likely ones with a dose of randomness. Ask the same question twice and you'll get two differently-worded, sometimes differently-structured, answers. That's not a malfunction; it's the design.

The dose of randomness is a setting called temperature. Low temperature (near 0) makes the model almost always pick the top candidate: consistent, repeatable, a bit flat. That is what you want for classification, extraction, or code. High temperature lets it explore less likely tokens: more varied and creative, but less predictable. That suits brainstorming and writing.

In 2026 this setting is disappearing from the most advanced models. On their newest reasoning models (next section), Anthropic, OpenAI and Google no longer let developers set temperature at all. Consistency now comes from clear instructions, a fixed output format and checks. Temperature still matters for older models and for open-weight models that you run yourself.

AnalogyA deterministic system is a vending machine: B4 gives you the same snack every single time. An LLM is a good chef: order the same dish twice and it will be recognizably the same dish, but never molecule-for-molecule identical. Temperature is how much you let the chef improvise.
Why it matters in practiceYou can't test GenAI like a script: asserting on exact output will fail. You evaluate it like you'd evaluate a person's work: on samples, against criteria ("is it accurate? grounded? in policy?"). For anything compliance-critical, give precise instructions and a fixed output format, lower the randomness where the model allows it, and add automatic checks around the output.

Reasoning models: thinking before answering

Since late 2024, the biggest change in LLMs is the reasoning model. Before writing its answer, a reasoning model first writes a long chain of intermediate steps, often called "thinking": it breaks the problem down, tries an approach, checks it, and corrects itself. Only then does it write the final answer. OpenAI's o1 (September 2024) was the first widely available one; Anthropic and Google followed in early 2025, and today most frontier models can think before they answer.

Nothing magic was added: thinking is still next-token prediction. What changed is the training. The model was rewarded for reaching correct answers on problems that a program can check, such as mathematics and code, and it learned that working step by step gets better results.

There are two practical consequences. First, thinking costs tokens: it is billed as output tokens, even when the product hides it, and it adds waiting time. Second, you can usually choose how much the model thinks, with a setting called effort or thinking level: high for a hard analysis, low for a simple task such as classifying a ticket.

AnalogyA classic LLM answers like a quiz contestant: the first answer that comes to mind, instantly. A reasoning model answers like an engineer with a notepad: it works the problem out on paper, checks the result, then gives the answer. The notepad takes time and paper; that is the price of better answers to hard problems.
Why it matters in practiceReasoning helps most on multi-step problems: troubleshooting, analysis, planning, maths and code. It does not add knowledge the model does not have, so it does not replace RAG for company data. And the written thinking is not a guaranteed true account of how the model reached its answer, so check the result, not only the reasoning.

Prompting basics: how to ask

The model only knows what is on the whiteboard, so the way you ask changes the answer a lot. Every request has two layers. The system prompt holds standing instructions written by whoever built the application: the assistant's role, its rules, its tone and its output format. It is placed on the whiteboard before every conversation, usually hidden from the user. The user prompt is what you type. Good prompts, in either layer, share five habits:

  • Context. Say who you are, who the answer is for, and why you need it. "Summarize this incident for a CIO who has two minutes" works better than "summarize this".
  • Task. Give one clear instruction and describe the result you expect.
  • Examples. Show one to three examples of good output. These are called few-shot examples, and they often work better than long descriptions.
  • Format. Ask for the structure you need: a table, three bullet points, a fixed template, a maximum length.
  • Rules for doubt. Tell the model what to do when it does not know, for example "If the documents don't say, answer 'not found'." This lowers hallucinations.
AnalogyPrompting is briefing a brilliant new contractor who knows nothing about your company and works only from your brief. Everything they need, including what "good" looks like, must be in the brief.
Why it matters in practiceMost disappointing results come from a vague prompt, not a weak model. Before blaming the model, add context, an example and a format. In an application, the system prompt is where the company's rules live, so it deserves the same review and testing as code.

Fine-tuning: onboarding the new hire

Fine-tuning means taking a trained model and training it a bit more on your own examples (support tickets, your writing style, your product docs) so the behavior becomes second nature. It changes the model itself, which is powerful but heavy. In practice, most companies get further with a good prompt plus RAG (next part) and only fine-tune when they need consistent style or a specialized domain at scale.

AnalogyRAG is handing a smart consultant your binder of documentation before the meeting. Fine-tuning is sending them to a three-week internal training. The consultant with the binder is cheaper, faster to update, and usually good enough.

Multimodal: beyond text

Early LLMs only handled text. A multimodal model also takes images, audio, video, or documents as input, and increasingly produces them as output. Under the hood it's the same trick: a screenshot is converted into tokens the model can process alongside your words. Practically, this is huge for IT: paste a screenshot of an error dialog, a photo of a rack, or an architecture diagram, and ask questions about it directly, with no transcribing.

AnalogyA text-only model is a brilliant colleague you can only reach by chat. A multimodal one is on a video call: you can share your screen and just say "look at this."
Nexthink exampleWorkspace accepts image attachments in a conversation: paste a screenshot of an error or a dashboard, and Assist uses it as context for its answer. That is the multimodal "screen-share" pattern, live in the product.

Open-weight vs proprietary: the build-vs-buy of AI

A proprietary model (GPT, Claude, Gemini) is used through the vendor's API or apps: state-of-the-art quality, zero infrastructure, but your prompts transit the vendor's cloud and you pay per token. An open-weight model (Llama, Mistral, Qwen, DeepSeek, gpt-oss…) can be downloaded and run on your own servers: full data control, no per-token fees, works air-gapped. But you own the GPUs, the operations and the updates, and quality typically trails the frontier models. Most enterprises end up hybrid: proprietary via API for general use, open-weight self-hosted where data can't leave.

AnalogyIt's SaaS vs self-hosted, exactly like the choice you've already made for email, CRM or monitoring. Same trade-off triangle: convenience and cutting-edge features vs control, sovereignty and predictable cost.
Nexthink exampleThere's a third way, and Nexthink uses it: consuming models through a managed cloud service (Amazon Bedrock) inside Nexthink's own AWS account, in the same geographical area (continent) where customer data is stored. You get frontier-class models and control over where data is processed, a pattern worth knowing when customers raise sovereignty concerns.

Part 2 / Grounding it in your data

Embeddings, vector databases & RAG

Key ideaAn LLM does not know your company. RAG finds the right documents at question time and puts them in front of the model, so it answers from your current data and can cite its sources. Updating knowledge means updating a document, not retraining a model.

Out of the box, an LLM knows nothing about your company: not your runbooks, not your pricing, not last Tuesday's incident. And its knowledge stops at its training cutoff date. The fix is not to retrain the model: it's to fetch the right documents at question time and put them on the whiteboard. That pattern is called RAG: Retrieval-Augmented Generation.

Embeddings: GPS coordinates for meaning

To fetch "the right documents," you need search that understands meaning, not just keywords. An embedding converts a piece of text into a long list of numbers (a vector) that captures what it's about. Texts with similar meaning land close together in that number space: "the laptop won't boot" ends up near "PC fails to start", even though they share almost no words.

Vector database: a library sorted by meaning

A vector database stores those embeddings and answers one question fast: "here's a vector, find the stored vectors closest to it." Chunk your documentation, embed each chunk, store the vectors, and you can retrieve the most relevant paragraphs for any question in milliseconds.

AnalogyA normal database is a library sorted alphabetically: great if you know the exact title. A vector database is a library where books about similar topics physically sit next to each other, so you walk to "printer problems" and every relevant book is on that shelf, whatever its title.

Putting it together: RAG

Why it matters: the model answers from your current documents, can cite its sources, and updating knowledge means updating a document, not retraining a model. This is the single most common pattern in enterprise GenAI today, and it's what most "chat with your data" products are underneath.

Nexthink exampleAsk Workspace a question and Assist retrieves before it answers: it queries Nexthink documentation, Infinity configuration objects (dashboards, library packs) and live data via NQL, then composes a grounded response with links to the underlying investigations. And AI Insights follows the same grounding principle with telemetry instead of documents: the impact analysis on an alert or the tooltip in Network View is generated from real collected data placed in the model's context, which is why it can explain root cause instead of guessing.
Part 3 / From answering to acting

Agentic AI, MCP & Agent2Agent

Key ideaAn LLM only predicts text. Everything trustworthy about modern AI comes from the system built around that predictor: real data (RAG), real actions (agents and MCP) and real collaboration between agents (A2A).

Agentic: giving the model hands

A plain LLM can only talk. An agent is an LLM placed inside a loop and given tools: search the web, query a database, call an API, run code, send an email. The loop looks like: think → pick a tool → use it → look at the result → decide the next step → repeat until done. "Agentic" describes systems built this way: the model doesn't just answer, it plans and executes multi-step work, adjusting as results come in.

AnalogyA plain LLM is a brilliant consultant on the phone: great advice, but they can't touch anything. An agent is the same consultant sitting at a workstation with your apps open: they can check the ticket queue, run the query, and draft the reply themselves.
Nexthink exampleSpark is this loop shipped as a product: a personal IT agent that understands an employee's issue in natural language, reasons over live device context from Infinity, pulls from knowledge sources (KB articles, past ticket insights, the automation catalog), then acts: it proposes manual steps or runs IT-approved remediations, and escalates to the service desk with full context when it can't resolve. Note the design choices that make an enterprise agent trustworthy: every action is pre-approved by IT, governed by policy guardrails, and fully logged. Autonomy without a black box.

MCP: one standard to connect AI to your systems

Historically, every tool connection was a custom integration: your CRM one way, your ticketing system another, each AI vendor requiring its own connector. MCP (Model Context Protocol) is an open standard that fixes this. A system exposes its capabilities once as an "MCP server" ("I can search tickets, create tickets, read a knowledge base"), and any MCP-compatible AI can plug in and use them, with no custom integration code for every AI-tool pairing. Anthropic published MCP in November 2024. In December 2025 it was donated to the Agentic AI Foundation, part of the Linux Foundation, which now governs it.

Agent2Agent (A2A): agents talking to each other

MCP connects an agent to tools. Agent2Agent (A2A) is a protocol for agents to talk to other agents: discover what another agent can do, hand off a task, and get results back, even across vendors and companies. Picture a procurement agent asking a supplier's agent for a quote, or an IT agent delegating a network diagnosis to a specialized network agent. Google launched A2A in April 2025 and gave it to the Linux Foundation in June 2025.

The two protocols are complementary. A2A is not built on MCP. A typical agent uses MCP to reach its own tools and data, and A2A to work with other agents.

AnalogyMCP gives one employee access to the tools on their desk. A2A is the company org chart and email system: it lets specialized colleagues find each other, delegate, and collaborate on a job too big for one person.

Part 4 / Spotting the real thing

What is (and isn't) agentic AI

Key ideaChatbots, RPA and simple RAG follow a path somebody drew in advance. An agentic system chooses its own path, within limits you set. The LLM is the same in both cases; what changes is the loop, the tools and the guardrails built around it.

"Agentic" has become the most overused word in AI marketing. Customers will hear it attached to chatbots, automation scripts and document search. Before you can have an honest conversation about it, you need a quick way to tell the real thing from the lookalikes. The test is simple: does the model itself decide what happens next, use tools to act, check its own results, and loop until the goal is met? If a human-written script or a fixed pipeline makes those decisions instead, it is not agentic, however much AI sits inside it.

Three setups that look agentic but are not

The three setups are an LLM chatbot, RPA (robotic process automation: scripts that follow fixed rules) with an LLM step, and simple RAG. All three use an LLM, and all three can be genuinely useful. What they lack is the loop: the path from question to answer is fixed in advance.

What a real agentic system adds

Part 5 / In the backend

Three prompts, explained step by step

Key ideaSame chat box, very different machinery. A plain LLM writes from memory, RAG adds your documents, and an agent fetches live data with tools. The architecture around the model decides whether the answer can be trusted.

Here's what actually runs in the backend for a simple prompt, a prompt grounded in your documents (RAG), and an agentic one.

Example 1: pure LLM (no tools, no data)

You type"Write a short apology email to a customer whose migration was delayed by two days."
1

Tokenization

Your sentence is split into ~20 tokens and converted to numbers. A hidden system prompt (the assistant's standing instructions: tone, rules, format) is placed on the whiteboard before your message.

2

One giant prediction pass

The model computes probabilities for the first token of the reply. From everything it has read, after an instruction like this, replies overwhelmingly start with something like Subject: or Dear.

3

Loop, one token at a time

The chosen token is appended to the whiteboard, and the model predicts the next one. Repeat a few hundred times. That's why answers stream word by word: you're literally watching the loop run.

4

Done

The model emits a special "stop" token. Total time: 2–5 seconds. Nothing was looked up. The email is good because millions of apology emails shaped the model's sense of what one looks like.

Example 2: LLM + RAG (your documents, but not agentic)

You type"What does our runbook say about renewing an expired certificate?"
1

Embed the question

The pipeline converts your question into an embedding, a list of numbers that captures its meaning. This step is hard-wired: every question goes through it, whatever it says.

2

Retrieve

The vector database returns the 3 runbook passages whose meaning is closest to the question. The model has not been involved yet: the retrieval is performed by the pipeline, once, in a fixed way.

3

Augment the prompt

The pipeline pastes those passages onto the whiteboard, next to the system prompt and your question, with an instruction such as answer only from the passages below.

4

Generate, one token at a time

From here it is Example 1 again: the LLM predicts the answer token by token, this time with the right text in front of it. The answer is grounded and can quote its source, for example [source: cert-renewal-runbook §3]. Total time: a few seconds.

5

Why it is not agentic

The model never decided anything. It did not choose to search, did not check whether the passages were sufficient, and could not try a second query or call another system. Ask this setup "How many P1 incidents did we have last month?" and it will still retrieve runbook text, which does not contain the answer. It will say it does not know, or worse, improvise a number. That gap is exactly what Example 3 closes.

Example 3: agentic + RAG (tools and your data)

You type"How many P1 incidents did we have last month, and what does our runbook say about the most frequent root cause?"
1

Plan

The LLM reads the question plus a list of tools it's been given (via MCP, for example: query_itsm, search_runbooks). It decides this needs two steps and can't be answered from memory.

2

Tool call #1: live data

It emits a structured request: query_itsm(priority="P1", period="last_month"). The platform executes it against the real ITSM system and pastes the result, 17 incidents, top cause: expired certificates (6), onto the whiteboard.

3

Tool call #2: RAG

Now it calls search_runbooks("expired certificate renewal procedure"). Behind that tool: the query is embedded, the vector DB returns the 3 closest runbook chunks, and those paragraphs land on the whiteboard too.

4

Verify & synthesize

The model now answers using only what's on the whiteboard: "17 P1s; most frequent cause was expired certificates (6 cases); the runbook prescribes… [source: cert-renewal-runbook §3]." The numbers are real because they were fetched, not remembered.

5

The difference

Ask Example 1's setup this question and it will hallucinate a plausible number. Ask Example 2's and it retrieves runbook text that cannot contain the number. Ask Example 3's and it fetches the truth. Same model: the architecture around it makes the difference.

The one-table cheat sheet

TermIn one sentence
Agent / AgenticAn LLM in a loop with tools: plan, act, observe, repeat.
Agent2Agent (A2A)Protocol for agents to discover each other and delegate tasks; complements MCP.
Context windowThe maximum amount of text the model can consider at once.
EmbeddingText converted to numbers so that similar meanings are numerically close.
Few-shot examplesA few examples of good output placed in the prompt to show the model what to do.
Fine-tuningExtra training on your examples to change the model's default behavior.
GenAIThe branch of ML whose output is new content (text, code, images) rather than a classification.
HallucinationA fluent, confident answer that happens to be wrong.
Human-in-the-loopA checkpoint where a person approves, corrects or stops an agent's action before it takes effect.
Input / output tokensWhat the model reads and what it writes; billed separately, with output tokens costing more.
LLMA model trained on massive text to predict the next token, over and over.
MCPOpen standard connecting any AI to any tool or data source, built once.
MLPrograms that learn patterns from examples instead of hand-written rules; outputs labels, scores, predictions.
MultimodalA model that also understands images, audio, and documents, not just text.
Neural networkLayers of simple units with learned weights that turn input numbers into output numbers; the inside of an LLM.
Open-weight vs proprietarySelf-host a downloadable model for control, or use a vendor's frontier model via API for quality and convenience.
OrchestratorThe LLM at the centre of an agentic system that plans, picks tools, delegates to other agents and decides when the job is done.
RAGRetrieve relevant documents first, then let the LLM answer from them.
Reasoning modelA model trained to write intermediate "thinking" steps before its answer; better on hard problems, slower and more expensive.
RPAScripted automation that follows fixed rules; it can call an LLM for one step but does not choose its own path.
System promptStanding instructions from the application (role, rules, tone, format), placed before every conversation.
TemperatureThe randomness dial: low = consistent and repeatable, high = varied and creative. Not available on the newest reasoning models.
TokenThe chunk of text (~3–4 chars) models actually read, write, and bill by.
Training / inferenceTraining builds the model once in the lab; inference is every use of the frozen model. Prompts don't retrain it.
Vector databaseA store optimized for "find me content similar to this."
